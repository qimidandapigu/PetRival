# 事件流记忆 + 第 7 关双人配合关（2026-09-17）

## 1. 尝试记录加入因果事件流

**日志诊断**（data/client-log.jsonl，15:16–16:19 时段）：宠物在第 2/6 关反复卡在关闭的门前（x=746、x=922、x=928），复盘 3 次仍在门前试跳。根因：机关必须**持钥匙且落地**踩到才生效（jump-world.mjs `touch`），宠物从机关上方跳过去没触发，而尝试记录只有 from/to/outcome/actions——**没有任何"经过机关时发生了什么"的数据**，模型于是把"关着的门"误判成"跳不过的缺口"。

**改动**：

- `public/jump.mjs`：宠物每帧步进后记录因果事件——`捡到金币@x` / `取得钥匙@x` / `踩下机关@x（门开了）` / `从机关上方飞过但没落地踩到@x` / `被关着的门挡住@x（机关未开）`。事件随当前尝试重置，尝试结束时附在情景卡上，并写进日志。
- `server/jump-model.mjs`：`attemptsInput` 透传 `events`（去重、≤8 条、每条 ≤48 字），情景卡系统提示词明确说明：**被关着的门挡住是门的问题，不是跳跃的问题，回头看机关和钥匙的事件**。决策与复盘共用同一结构，复盘证据 id 机制不变。
- 零模型成本：事件在客户端逐帧采集，只是字段。

测试：`test/jump-ui.test.mjs` 新增——第 5 关走过金币、被关闭的门挡住，情景卡含两条事件。

## 2. 第 7 关「并肩作战」：双人配合关

**机制**（引擎新增，全部向后兼容、非配合关行为不变）：

- `level.coop.plates`：两块压力板（校验：恰好两块、坐标合法、相距 ≥96px——一个人踩不住两块）。
- 共享世界状态 `worldProgress()`：金币、钥匙、门闩为双方共有，谁捡到都算。
- 门闩 `latchPlates()`：两块板**同一时刻都被踩住**（任一方）→ 门永久打开。单侧进度只记各自的 `won`。
- 通关条件：共享金币收齐 + 共享钥匙 + 门闩已开 + **双方各自走到终点**。宠物在终点等待时世界不停（人可以继续走）。
- 配合关里地面机关 `s` 不参与开门（地图改画压力板 P 和主人 H）。

**关卡**（`stageLevel(7)`，1200 宽平地）：金币 x=200/600、钥匙 x=460、压力板 x=300 与 x=700、门 x=820、终点 x=1080。一个人在 300 踩板，另一个人在 700 踩板 → 门开 → 各自走到终点。

**宠物怎么理解它**：决策上下文新增——字符地图画 `H`（主人）与 `P`（压力板）、coop 图例、输入里的 `partner {x,y,dead,won}`，系统提示词说明配合规则（共享拾取、双板同踩开门、踩着不动是 `{move:0,jump:false}`、双方都要到终点）。预取推演把主人当静止旁观者参与门闩判定。

**测试**（`test/jump-stages.test.mjs`）：单人走全图门闩永不触发、被门挡在 806；双人脚本（人踩左板、精灵跨图踩右板）门闩打开、共享金币/钥匙、双方到终点通关。阶梯测试更新为 7 关。画布上压力板按"未被踩 / 被踩 / 门已开"三态着色。

## 限制

- 配合关没有有界求解器验证（单人不可解是设计使然）；改为脚本化双人回放验证。
- 预取推演假设主人静止：主人若离板，预取段里的"门开"可能不发生——按既有"推演不符即作废重算"处理。
- 预测命中率（日志中约 50%）本轮未直接优化；事件流先解决"学错因果"这个更根本的问题。
